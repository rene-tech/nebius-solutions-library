# Adapter-to-image contract

This is the handoff for the scientific batch adapter owner, who keeps the typed
public request schema and translates it into this image's CLI.

**The image's CLI and its internal `fs2-serve.nebius.ai/rfdiffusion-parameters/v1`
schema are frozen for the duration of that work.** Nothing here will change
incompatibly. If the contract needs to move, it moves by adding a new fixture and a
new adapter id, never by redefining an existing one.

## What the adapter must produce

Two files and a mount. Nothing else.

| Path in container | What |
| --- | --- |
| `/var/run/fs2/request.json` | `scientific-run-request/v1` whose `parameters` are `rfdiffusion-parameters/v1` |
| `/var/run/fs2/input-manifest.json` | `scientific-artifact-manifest/v1` listing every artifact by id, **relative** path, sha256 and size |
| `--artifact-root` | read-only mount whose tree contains those relative paths |

The image resolves the checkpoint and any target structure *through the manifest's
relative paths*, so the adapter chooses the mount point, not the image. It never
hard-codes `/models/rfdiffusion` or `/models/rfdiffusion-checkpoints`.

**Delivery is mixed-plane.** Each plane is mounted read-only at
`<artifact-root>/<plane-name>`, and manifest paths begin with the plane name, so one
run can draw the checkpoint from a public plane and another artifact from a
licence-restricted plane without either plane hosting the other's bytes.
`render_job.py` takes repeatable `--plane NAME=CLAIM[:SUBPATH]` and refuses to run
with none, so a single-claim default cannot be inherited by accident. RFdiffusion
itself needs only the `public` plane: its code and weights are BSD-3-Clause and the
1UBQ target is public PDB data, so this runtime never mounts a restricted plane.

## Fixtures

Each directory under `fixtures/` is a complete, runnable example:

```
fixtures/design-backbone/    request.json  input-manifest.json  golden-argv.json
fixtures/scaffold-motif/     request.json  input-manifest.json  golden-argv.json  1UBQ.pdb
```

`golden-argv.json` records, for that exact request:

- `image_invocation` — the argv the Job's container must run
- `upstream_argv` — the argv this image will then execute against upstream
- `required_artifacts` — every artifact id with its relative path, sha256, size and
  resolved container path
- `expected_markers` — the files upstream must write, relative to `--output`
- `design_indices` — which design indices the seed maps onto
- `requested_residues` — the residue window verification will enforce

Golden files are generated by the image's own `build_argv`, never hand-written:

```bash
python3 contract/generate_golden_argv.py           # regenerate
python3 contract/generate_golden_argv.py --check   # fail if stale
```

`--check` runs in `run_checks.sh`, so the golden argv cannot silently drift from the
runtime. `ContractFixtureTests` additionally drives the real `main()` against
`fixtures/*/request.json` and asserts the executed argv equals `upstream_argv`, so
the contract is verified end to end rather than by inspection.

## The two operations

**`design-backbone`** — unconditional monomer. Contigs carry no motif span and no
`input_pdb_artifact_id`. Output is an all-glycine backbone.

**`scaffold-motif`** — requires at least one motif span in contigs *and* an
`input_pdb_artifact_id` naming a structure in the manifest. The image verifies motif
survival from upstream's own `con_ref_pdb_idx`/`con_hal_pdb_idx` mapping: residue
identity must be unchanged at every mapped position, and motif CA RMSD must be within
`motif_ca_rmsd_limit` (default 1.5 Å).

## Seeds

There is no `inference.seed` in RFdiffusion v1.1.0. A seed maps onto
`inference.design_startnum` with `inference.deterministic=True`, so design *i* is
seeded by its own index. `golden-argv.json.design_indices` states which indices a
request produces; the result envelope reports the index that seeded each design.
Do not translate a public seed into `inference.seed=` — that key does not exist.

## Result

The image writes `<output>/result.json`, a
`fs2-serve.nebius.ai/scientific-run-result/v1` envelope. `status` is `succeeded`
only after every marker verified, the checkpoint digest matched, and upstream's
`.trb` recorded a CUDA device. A failed run still writes a truthful envelope with
`error.type` and `error.message`, so the adapter can classify without parsing logs.

Exit code is 0 on success and 1 on any terminal failure. `RequestError` means the
request was malformed or out of bounds and is not retryable; `VerificationError`
means upstream ran but its artifacts did not satisfy the contract.
