## Distributed execution

The `gromacs-mpi` App has its own typed `submit_gromacs_mpi_workflow` tool. It
accepts one logical workflow with an explicit node count; each rank uses one GPU
and up to eight CPU threads. The current qualified native configuration is two
H100 nodes; a wider schema range is not evidence for untested node counts.

The platform reuses PostgreSQL Operations, Kueue and JobSet. The JobSet supplies
per-attempt DNS, complete-gang ownership and distinct-node placement. Rank zero
does preprocessing/analysis and publishes the authoritative native checkpoint.
Generated TPRs, updated checkpoints and other native MD inputs are transferred
to peers before launch, streamed and hash-verified with atomic installation.
Unchanged inputs are not resent. No customer storage credential is given to the
simulation process. No new scheduler, driver or GPU partition was installed.

The baseline uses host-staged TCP, not GPU-direct/RDMA. A large public STMV system
contains 1,066,628 atoms. Native two-node operational measurements:

| Fixture | Steps | Wrapper, restart and collection wall |
| --- | ---: | ---: |
| Development image, automatic PME | 20,000 | 821.606 s |
| Development image, explicit one GPU PME rank | 20,000 | 673.770 s |
| Exact final image, explicit GPU PME | 6,000 | 202.965 s |

The same final external-MPI engine on one H100, eight threads, identical 6,000-step
TPR `c87a794c9cb8c787ae55d47dd39bc1589ab518aa9710bdf700db5fa2b864bd20`, three
repetitions per layout: automatic median **30.875 ns/day**, explicit GPU-resident
median **31.651 ns/day**. Two-node segment logs are around 6–7 ns/day. Checkpoint
and transfer overhead differ between these two execution shapes, so these are
not a clean network-only strong-scaling comparison. They do establish that the
present two-node TCP setup is not a speed upgrade. Single GPU remains the default.

A full-node pair could not be admitted without disturbing occupied customer
GPUs. Only our pending probe was removed. No full-node/RDMA performance claim.
Coupled replica exchange, scheduler-owned MPS ensembles, CPU→GPU→CPU stage
separation and automatic placement based on these measurements remain unpromoted.

## Separate NNPot and CP2K evaluation

The NVIDIA engine does not contain Torch or CP2K. A separate reproducible NNPot
build with LibTorch 2.10/CUDA 13 passed **all 18 upstream NNPot unit tests on
H100**. This is build/GPU feasibility, not hosted scientific workflow acceptance,
an arbitrary potential's accuracy test, or permission to expose an NNPot App.
Its image is `gromacs@sha256:6a4ade874d9a0fcd00cc4b8db1806de2bef5ad7894c7bd203044aaea2881568c`.

CP2K integration requires a separate static build with compatible FFT/BLAS/LAPACK;
upstream recommends double-precision GROMACS and disabling GMXAPI/NBLIB. It is
not a drop-in performance switch for the optimized NGC image. QM/MM also has
important scientific restrictions: topology changes are not supported, B-state
parameters are ignored for these interactions, and missing QM/MM force virial
can affect constant-pressure simulations. A specific reference protocol and
numerical validation are needed before publishing a customer execution shape.

Sources: [GROMACS 2026.2 installation](https://manual.gromacs.org/2026.2/install-guide/index.html),
[NNPot](https://manual.gromacs.org/2026.2/reference-manual/special/nnpot.html),
[QM/MM](https://manual.gromacs.org/2026.2/reference-manual/special/qmmm.html).

## Failures retained and fixed

- MPI peer launch used the old Open MPI remote-launch option: corrected to the
  PRRTE SSH interface and qualified private per-attempt bootstrap.
- Preprocessing creates a TPR on rank zero, not on every peer: added streamed,
  verified changed-input staging before every launch/restart.
- The initial full-node probe lacked two available distinct nodes; no MD ran.
- The first L40S release fixture used the wrong job ID; fixed the qualification
  helper's single-job selection. This was an operator harness failure.
- NNPot tests need a real CUDA device and a writable compiled test-temp path;
  final H100 run passed all 18, previous failures remain in private evidence.
- Hosted discovery hid variable-size MPI gangs because no run-specific gang
  size exists during listing. Added a failing regression and fixed discovery to
  validate the minimum legal gang without changing submission bounds.
- Hosted MPI peer eviction originally became a terminal application error:
  Open MPI aborts the surviving rank with exit 1. Backend `12cea92f4` correlates
  the complete gang's explicit disruption timestamps, preserving earlier
  application failures, OOMs and deadlines. 122 focused observer tests and 55
  controller/adapter tests passed. Real repeat `98d3798b-c7e1-458c-b75e-e3fef01b3562`
  classified the eviction as infrastructure and automatically started attempt 2.
- That repeat then failed exporting to the full customer bucket. An independent
  73,597,387-byte S3Transfer probe returned HTTP 400 `BucketMaxSizeExceeded`, with
  both default and required-only SDK checksum modes. No quota was increased.
  The failed operations `d4b5dfc4-2bc2-45e2-84a8-14c500763371` and
  `98d3798b-c7e1-458c-b75e-e3fef01b3562` were archived byte-for-byte before deleting
  their 47 task-owned exported objects, freeing 823,412,662 bytes. Exact keys,
  metadata, hashes and file bytes remain under the private evidence root's
  `archived-mpi-recovery-r1` / `archived-mpi-recovery-r2` directories. No other
  customer operation prefix was removed. Successful result retention is unchanged.
- Backend `f1ce1c70d` retains bounded S3 provider codes/HTTP status in failures,
  without exposing provider URLs or credentials. Paired GROMACS updates now
  replace both execution identities together while retaining the other 11 App
  rows and their qualification proofs. Storage/adapter tests: 38 passed;
  activation tests: six passed. Original failing runs stay failed in the ledger.

MPI cancellation `6ac88364-d1c3-4052-ba13-101fbc519af6` finished with both GPUs
released and zero remaining Pods after **131.908 s**. This includes the configured
120-second termination grace; it is functional but not instant. No final
post-cancellation checkpoint is promised. The cancellation exported zero objects.

Final hosted recovery on Helm 222, operation
`647af3b7-1ca4-42bc-ba49-47f17650729b`, **passed**. After the peer was evicted at
committed generation 2, the controller started attempt 2 without another client
submission. The 6,000-step STMV simulation completed in **346.492 s** from

There is no persistent CUDA/CRIU snapshot claim. Native GROMACS checkpoints,
including bias files and segmented trajectories, are the recovery mechanism.
