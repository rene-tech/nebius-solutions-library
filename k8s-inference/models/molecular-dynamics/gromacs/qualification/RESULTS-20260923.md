## CUDA state suspend/resume feasibility

On the same H100/driver 580.173.02, the official NVIDIA `cuda-checkpoint` binary
from commit `00d5cce84c628088d6caa203fc4af40c1538b6f7` suspended and resumed a
running candidate5 `mdrun`. Binary SHA-256:
`707fa7f54136824d6c1d6dd724b9b1717610f831033c00d06da474de363a06db`.
The 400 ps process completed with exit zero after the probe.

- Native startup log reached in 3.359 s.
- GPU checkpoint action: 0.435 s; restore action: 0.266 s.
- Lock/unlock: 0.015/0.016 s; whole process including probe: 30.077 s.

Evidence: `h100-cuda-suspend-v1`. This is **GPU-state suspend/resume inside the
same living process**, not CRIU disk persistence, a new Pod cold start, or a
customer-facing snapshot option. No such option is enabled. Native `.cpt`
continuation remains the portable durable recovery mechanism. Measure total
queue/image/input/restore time before investing in a process snapshot to save
only a few seconds of initialization. Never clone stochastic state and call
the clones independent replicas. See
[NVIDIA's checkpoint documentation](https://github.com/NVIDIA/cuda-checkpoint/blob/00d5cce84c628088d6caa203fc4af40c1538b6f7/README.md).

## Failures that were found and addressed

1. A pre-neutralization fixture TPR used PME with a net charge. Corrected only the
   ion-placement preparation to cutoff electrostatics; all actual MD uses PME
   after neutralization. No `-maxwarn` was added to hide the warning.
2. `mdrun -noappend` writes numbered final coordinates, not just numbered
   trajectories. The runner now retains every part and supplies the ordinary
   final-coordinate path for subsequent explicit steps.
3. One prior regression invocation used a different worktree's installed package.
   The new shared runtime is now packaged in this worktree's own locked virtualenv.
