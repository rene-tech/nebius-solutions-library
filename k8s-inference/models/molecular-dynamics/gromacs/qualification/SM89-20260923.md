## Build proof and regression guard

`Containerfile.native` uses the version's supported
`CMAKE_CUDA_ARCHITECTURES=75;80;86;89;90`; numeric CMake targets retain PTX as
well as native cubins. The build runs `cuobjdump --list-elf` on the installed
library and fails if required targets are missing or have unequal cubin counts.
This is compiled-code evidence, not a label or compiler-option assertion.

Candidate `libgromacs.so.11` SHA-256 is
`7983a1afa01bb6b588d09939f3129e988d2ca5f2ad39a44215958195624db127`.
There are **52 cubins for each of SM75, SM80, SM86, SM89, and SM90**.
Independent `cuobjdump --list-ptx` also finds retained PTX for those targets.
The original NGC executable has cubins and PTX for 75/80/86/90 and none for 89.

The warning about absent SM89 does not by itself prove PTX JIT is used or impose
a measured slowdown. CUDA permits SM86 cubins to execute on SM89. A separate
`CUDA_DISABLE_PTX_JIT=1` run tests compatible binary execution; fresh/warm cache
counts alone cannot identify whether cached work came from GROMACS or cuFFT.
[CUDA binary compatibility](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html),
[CUDA dispatch environment variables](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html).

The current NGC image's full STMV diagnostic with `CUDA_DISABLE_PTX_JIT=1`
failed at `cufftPlanMany` creation (error 5), before integration. This is retained
as a failed diagnostic, not dropped from the ledger. A separate 1,000-step
diagnostic moved only PME execution to CPU and explicitly kept nonbonded,
bonded, and update work on GPU. It completed with PTX JIT disabled. This proves
compatible cubins execute the exercised GROMACS GPU paths on L40S. It does not
identify every kernel in an automatic full-PME run or measure an SM89 speedup;
the changed-offload, shorter diagnostic is excluded from performance comparison.

## Cost boundary

Prices were rechecked on 23 September 2026. The actual L40S node's compute-only
on-demand rate is **$1.7468/hour**: one GPU at $1.35, 16 vCPU at $0.012 each,
and 64 GiB at $0.0032 each. An equivalent preemptible allocation would be
$0.8484/hour; this node and its measurements are on-demand.
[Nebius Compute pricing](https://docs.nebius.com/compute/resources/pricing).

`compute USD/microsecond = allocation USD/hour × 24000 / measured ns/day`.
The new baseline projects $1,653.84/microsecond on demand, or $803.25 using
preemptible prices with unchanged performance and no interruptions. The latter
is a price projection, not a measured preemptible result. Disk, startup, I/O,
queuing, recovery, platform overhead, taxes and margin are excluded.

For the native candidate's automatic configuration, the corresponding estimates
are $1,690.93 on demand and $821.26 with projected preemptible prices. These are
engine-throughput-derived estimates, not bills. A second short-run view uses
`effective ns/day = 0.04 ns × 86400 / median process wall seconds`, retaining
measured process startup/output: the baseline's 142.855 s wall gives 24.192
effective ns/day and $1,732.91/microsecond on demand; the native candidate's
146.002 s gives 23.671 and $1,771.08. This still excludes image pull, scheduling,
artifact transfer, verification work, recovery and other platform overhead.

The task's external minimum-cost comparison is $1,349.75/microsecond on Fovus
optimized spot capacity, a different runtime and latency tier. At the actual
on-demand compute rate, 31.060 ns/day would match that unit cost before any
overhead or markup. The present baseline has no positive markup headroom at
that target. This is an economic comparison, not an engineering acceptance
threshold or a promised single-GPU performance target.
[Fovus's published study](https://www.fovus.co/2025/02/11/run-molecular-dynamics-simulations-in-the-cloud-as-fast-as-1139-ns-day-as-cost-effective-as-29-%CE%BCs-benchmarking-gromacs-on-fovus/).

## Reproduction

Build from the pinned recipe in `runtime/` with an explicit unique tag and source
revision. Keep default architecture coverage for a candidate; the no-89 override
below is intentionally only a benchmark control:

```bash
docker buildx build --platform linux/amd64 -f Containerfile.native \
  --build-arg SOURCE_REVISION=<exact-source-commit> \
  --tag <candidate-tag> --metadata-file <candidate-build.json> --push .
docker buildx build --platform linux/amd64 -f Containerfile.native \
  --build-arg SOURCE_REVISION=<same-source-commit> \
  --build-arg 'CUDA_ARCHITECTURES=75;80;86;90' \
  --tag <control-tag> --metadata-file <control-build.json> --push .
```

Resolve and use immutable image digests for Pods. In a task-owned single-GPU
Pod with the recorded eight-CPU quota and unmodified fixture, run:

```bash
python3 benchmark_sm89.py \
  --binary /opt/gromacs-native/bin/gmx --tpr /mnt/fs2-scientific/stmv.tpr \
  --sha256 b130030dd5a87dd15c3edd72812f64676559e609ab22b7ad0c366f655b922555 \
  --output /mnt/fs2-scientific/unique-cohort \
  --expected-steps 20000 --expected-time-ps 40
```

Use `/usr/local/gromacs/avx2_256/bin/gmx` for the retained NGC executable. The
same-source control and candidate use the same `/opt/gromacs-native/bin/gmx`
path in their respective images. Each output directory must be new. Keep the
three warmed repetitions; a `--warm-repetitions 0` run is a screen or diagnostic,
not confirmation. `summarize_sm89.py` verifies every retained output hash before
computing medians, spread, process CPU/GPU/power and timing-bucket summaries.

For the opt-in, input-specific bonded-GPU recipe, add `--bonded gpu` to that
command. The measured scope is this exact STMV TPR on one L40S with eight
threads and one rank. It is not a new hosted API option or default, and no
unrestricted arbitrary-argument surface is introduced. Requalify another
molecule, sampling protocol, output cadence or hardware before recommending it.

Tuning uses the same TPR and changes only explicit execution options:
`--pin on`, `--bonded gpu`, or `--nstlist 300`, one at a time. Increased CPU
allocation and thread count must be recorded separately. Sixteen-thread direct
probes do not extend the currently published eight-thread workflow schema.

## Decision and remaining gates

The build/proof/measurement work is ready for integration review. Preserve the
native-SM89 recipe and regression guard, the immutable candidate/control images,
and the per-protocol opt-in result. Do not replace the live image or change a
global offload, affinity, neighbor-list or thread-count default from this study.

Not tested here: image-pull or node-cold startup, isolated CUDA/JIT time,
autotuning-excluded long-run throughput, preemptible interruptions, candidate
hosted API/MCP admission/export/cancellation, candidate customer-bucket recovery,
or a persistent fresh-worker GPU snapshot. Those remain explicit limitations,
not passed release gates. Ordinary native checkpoint continuation was tested;
it must not be relabelled a GPU snapshot.
