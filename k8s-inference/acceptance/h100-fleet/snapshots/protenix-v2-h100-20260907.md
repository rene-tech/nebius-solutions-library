# Protenix v2: optional H100 GPU snapshot qualification

Three matched normal/restore pairs passed on 7 September 2026. Every fresh
worker executed both unchanged scientific wrappers: a 42-residue input with
seed 101, and a distinct 76-residue input with seeds 101 and 102. All expected
CIF structures, finite coordinates and original runtime/provenance/output
checks passed. This is a real CUDA + CRIU restore after donor Pod deletion,
not a retained GPU process or weights-only cache.

| Clock, median (range), 3 runs each | Normal loading | Snapshot restore |
| --- | ---: | ---: |
| Container start → observed model-ready | 66.253s (65.708–69.079) | 3.757s (3.718–4.051) |
| Pod-create request → observed model-ready | 70.558s (70.405–73.614) | 8.151s (8.018–8.364) |
| Container start → first fully validated structure | 85.325s (84.646–88.602) | 23.759s (22.832–24.546) |

The ready boundary is an HTTP response after immutable model initialization
and CUDA synchronization. Request-specific compilation is excluded. First
structure timing additionally includes the harness's post-ready fixture copy,
execution and validation, so it is not a pure inference benchmark. Restored
health responses retain the donor's historical loader duration; that value is
explicitly **not** used as restore timing. Kubernetes container timestamps have
one-second resolution, and polling/exec transport adds observation overhead.

These measurements retain existing image, model and shared-filesystem caches.
They do not claim disk-cold startup, node acquisition, image-pull avoidance,
reserved host RAM or cross-GPU-family portability. An earlier network-SSD
restore took about 86.8s, slower than its normal loader; storage/cache state
materially changes the result. A separate shared-filesystem restore across
the two H100 nodes passed with GPU UUID remapping: CPU restore 4.056s, CUDA
restore 0.508s, unlock 0.026s. That component clock excludes Pod startup.

## Immutable integration contract

The [qualification JSON](protenix-v2-h100-20260907.json) contains all six trials,
timings, semantic output hashes and exact compatibility. The
[bundle entry](protenix-v2-bundle.json) provides the production registry input.
Its 5,480,417,569-byte bundle contains 221 files; canonical file-manifest SHA-256
is `a2953619c0d2639aa9582771b5ee7778544328fe59e1b709a6c8da6221f67a24`.
The manifest includes file content, mode, UID and GID. It was hashed read-only.

- Base image, BF16 precision, 10 cycles, 200 diffusion steps and all original
  artifact checks remain unchanged. There is one sample per seed, no MSA,
  templates or RNA.
- Only the `sample-structure` stage uses the optional bridge. Its original
  command and UID/GID 10001 are preserved; preparation and collectors remain
  the normal scientific pipeline.
- The immutable `protenix-r2` bundle lives on the existing regional shared
  filesystem. Images are mounted read-only at the captured absolute path;
  each restored Pod gets its own mutable cache, temporary files and log.
- Exact runtime/tools images, model revision, four source-file hashes, driver
  580.159.04, H100 80GB SM90 and kernel identity are checked before restore.
  Incompatible or failed restoration falls back to normal model loading.
- Normal loading remains the default. Isolated qualification is complete;
  production registry/Terraform/admin wiring and its real submitted workflow
  acceptance are tracked separately. The matrix does not advertise an option
  before that rollout passes.

The input-free donor was deleted before restoration. All six matched-trial
GPU Pods were deleted after their artifacts and logs were retained. The
immutable bundle remains available for the production rollout.
