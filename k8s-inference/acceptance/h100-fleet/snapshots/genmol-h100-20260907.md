# GenMol: optional H100 GPU snapshot qualification

Three matched normal/restore pairs passed on 7 September 2026. Every fresh
worker ran the unchanged digest-pinned GenMol server and both pinned QED and
LogP requests. All generated molecules were parseable, had finite scores, and
matched independent RDKit recomputation within the original tolerances. The
donor Pod was deleted before the restore trials; this is a real CUDA + CRIU
restore rather than a retained GPU process.

| Clock, median (range), 3 runs each | Normal loading | Snapshot restore |
| --- | ---: | ---: |
| Container start → observed model-ready | 12.198s (11.729–14.349) | 8.654s (8.333–9.521) |
| Pod-create request → observed model-ready | 17.424s (17.408–65.558) | 14.604s (14.581–59.198) |
| Container start → both validated outputs | 29.628s (29.164–31.289) | 25.317s (25.099–26.368) |

The ready boundary is the application HTTP health endpoint after the snapshot
supervisor completed CUDA + CRIU restoration. The first pair included roughly
50 seconds of scheduler/init-container delay in both modes; this is why the
Pod-request ranges are wide while the container-start clocks are stable.
Request-specific work may still occur after readiness. The full-output clock
includes two sequential requests, client transport, and validation, so it is
not a pure inference benchmark.

These measurements retain existing regional image, localized-weight, and
shared-filesystem caches. They do not measure disk-cold startup, node
acquisition, an image pull, reserved host RAM, or another GPU family. Under
this already-cached condition, snapshot restore improves the median
container-to-ready clock by 3.544 seconds (29.1%); normal loading therefore
remains the default until the production bundle is explicitly selected and
its live fallback rollout passes.

The earlier cohort qualification reported a 96.121-second median from three
isolated Jobs using a task-owned 16 GiB block PVC and its `/models/home`
layout. This paired snapshot experiment instead clones the current production
Deployment, whose already-hydrated regional RWX weight volume and
ABI-namespaced runtime-cache paths are retained. Both use the same immutable
image, model revision, resources, and CUDA-ready model boundary, but the
storage/cache state and launcher environment are not equivalent. The old
96.121-second value is therefore useful historical startup evidence, not the
normal baseline for this pair. Only the matched 12.198s-versus-8.654s
container clocks support the snapshot speed comparison; this experiment does
not isolate which individual cache accounts for the baseline reduction.

## Immutable evidence

The [qualification JSON](genmol-h100-20260907.json) contains all six fresh-Pod
trials, output hashes, exact runtime compatibility, and hashes of the private
raw receipts. The published snapshot bundle is 4,704,296,927 bytes across 235
entries. Its canonical content-and-filesystem-metadata manifest SHA-256 is
`24256fa84376c40814ef25db41cda7b850c6199c7839c1e6ff97fc8ef76fee32`.

- Runtime image: `genmol@sha256:7a89a6f254e5a56dad391b8707315f8abd77d7138cacd585c706f63440463aaf`.
- Model revision: `2acccbd6eee62f2a90334ccf14dc7d2b17ef9e80`.
- H100 80 GB, SM90, driver `580.159.04`, kernel `6.11.0-1016-nvidia`.
- Capture components: CUDA checkpoint 1.256s, CRIU dump 47.687s, durable
  flush 0.346s.
- The capture-only process needed `CAP_SYS_RESOURCE` so CRIU could read the
  production-UID worker's rlimits. Restore does not receive that capability.

An earlier capture attempt without that capability failed at CRIU's
cross-UID `prlimit` read and is retained as negative evidence. An early
multi-model log glob also collected unrelated worker-log text; those polluted
copies are excluded. Trial timing comes from the individual Pod lifecycle and
health timestamps, while semantics come from the per-trial request/response
receipts. All six trial Pods and the publication Pod were deleted after their
evidence was retained; the read-only snapshot bundle remains on the existing
regional shared filesystem.
