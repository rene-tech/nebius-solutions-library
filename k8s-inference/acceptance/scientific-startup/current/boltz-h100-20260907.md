# BoltzGen design-stage startup — H100, 7 September 2026

All three fresh-process trials passed. Each ran the current, unchanged
20-candidate design stage on one H100 and validated all 20 generated two-chain
complexes, finite atom coordinates, metadata and accepted binder lengths.

| Clock | Median | Range |
|---|---:|---:|
| Container start → initialized | 36.05 s | 33.90–36.16 s |
| Pod creation → initialized | 44.16 s | 42.90–45.05 s |
| Relevant Python process → initialized | 32.49 s | 30.62–32.52 s |
| Container start → complete validated design output | 288.32 s | 286.20–306.05 s |
| Pod creation → complete validated design output | 296.32 s | 295.20–315.05 s |

The initialization timestamp is emitted **inside the native prediction
process**, after `_PredictionLoop._on_predict_start` returns and CUDA work is
synchronized. Lightning has performed checkpoint restoration and device setup.
The native hook source is hashed in each receipt. `LOCAL_RANK`, generic
weight-loading messages and buffered progress-bar arrival times are not used
as readiness. Lazy first-shape compilation remains part of prediction.

These are **cached-image/weight, fresh-process** observations, not disk-cold
loading or GPU snapshot restores. The accepted runtime image, both immutable
model/reference-data mounts, configuration artifact, precision, commands and
resources were retained. H100 80GB HBM3, SM90, PyTorch 2.7.1+cu126. Trials ran
on separately allocated GPUs and overlapped on the two retained reserved H100
nodes, alongside other authorized probes; this is not dedicated-node maximum
performance. Kubernetes timestamps have one-second granularity.

The source controller had removed its original Job, so
`boltz_recover_template.py` recovered the exact admitted design Pod spec from
the private timestamped watch (source Pod UID and spec hash are in the report).
`primary_isolated_runs.py` fetched the corresponding input artifact through
the authorized public API, checked its frozen size/digest, and passed those
same bytes to the existing materializer. Each clone used a fresh work
`emptyDir`. Benchmark-only import hooks and a supervisor were mounted; the
original uploader was omitted so completed source operations were untouched.

This measures the **design stage**, not the full public multistage workflow.
Later inverse-folding, refolding, filtering and analysis stages have their own
initialization. The complete 20-candidate output time above is deliberately
not called startup, first-token latency or scientific affinity validation.

## Reproduce

First capture an accepted current design Job with `primary_run.py`; if only
the full Pod watch remains, recover the exact source with
`boltz_recover_template.py`. From `k8s-inference`:

```bash
python3 acceptance/scientific-startup/current/primary_isolated_runs.py \
  --jobs-file /private/accepted-design-job.json --model boltzgen --stage design \
  --repetitions 3 --outputs /private/final-stack-output.json \
  --kubeconfig /private/kubeconfig --context k8s-inference-h100 \
  --repository-root /path/to/k8s-inference \
  --receipts /private/new-boltz-startup --suffix unique \
  --hook-file acceptance/scientific-startup/current/boltz_sitecustomize.py \
  --supervisor-file acceptance/scientific-startup/current/boltz_supervise.py
```

For overlapping starts, use one repetition per invocation and unique suffixes
and private receipt directories. `boltz_summarize.py` takes three `--receipt`
paths and the private `--source-template`; it rejects incomplete, duplicate or
contract-mismatched trials. Source templates and raw Pod data contain private
workload handles and must not be published.

[Machine-readable measurements](boltz-h100-20260907.json) retain individual
clocks, output hashes and artifact identities. The hook's two CPU tests passed,
and all three actual GPU trials passed. All three task-owned Jobs, Pods and
their six ConfigMaps were removed; production was not changed.
